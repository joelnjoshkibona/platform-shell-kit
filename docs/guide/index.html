Building a product on the platform kit

This guide explains, from the beginning, how a product is designed and built on the platform kit. It is written for someone who has never seen the kit: every term is explained the first time it appears, every step says which files it touches, which commands to run and how to check that it worked.

#What you will learn

  • What a "product" on this platform is, and the pieces it is made of (an API, a web app, a phone app, a prototype and its documents).
  • How decisions are made and written down, so nobody re-argues them.
  • Why every product starts as a clickable prototype, and how to make one.
  • How the code is organised: one folder per module, on every side.
  • The life of a module, from an idea to a released feature, and how it is changed or retired later.
  • How to build one module end to end, with real code.
  • How lists, details pages, forms and links work, on the web and on the phone.
  • How the work is tested, planned, tracked and explained (this guide is one of the deliverables).
  • How a product is released and run.

#How to read it

Read chapters 1 to 5 once, in order: they give you the map. Chapter 6 is a tutorial you follow with your hands on the keyboard. The later chapters are reference: come back to them when you need them. Words in code style are file names, commands or names in the code. The glossary at the end explains the platform's own words.

Note. Each product has its own build guide too, made from templates/guide/. The product's guide explains that product (its modules, its data, how each part was built). This kit guide explains what every product shares.

#The three promises

  1. The shell is decided. Sign-in, the sidebar, lists, details pages, forms, approvals, the phone app's behaviour: all decided once for every product (the "P" decisions). A product adds its own modules and never re-designs the shell.
  2. Design before code. A product is designed as a clickable prototype first, with its decisions written down. The code then builds exactly that.
  3. Anyone can rebuild it. The implementation plan, the progress tracker and the build guide are updated with every change, so a new developer (or an agent) can follow them and build the product again without asking.

#How they talk

 person ──► web app (web/)  ──┐
                              ├──► API (api/) ──► database
 person ──► phone app (mobile/)┘
  • The web app and the phone app never touch the database. They call the API over HTTPS with a sign-in token, and show what it returns.
  • The API checks who is asking (sign-in), what they may do (permissions, named like Tasks.create) and where (their organisation and locations), then reads or writes the database.
  • The prototype is not connected to anything. It holds its own fake data so a screen can be clicked and judged before any code exists.

#The core every product inherits

Every product gets these modules from the platform without writing them: users, roles and permissions, organisations, locations (a tree of branches, zones and regions), settings, menus, media (files), drafts, approvals and notifications, statuses, the dashboard and global search, and the system screens (P97): logs of who did what and what went wrong, the queue of background work, scheduled tasks, the trash, notification rules and announcements, and who has which permission. A product adds its own modules (Fomu: forms and responses; Shelui Tasks: tasks, tickets, projects).

Why. Writing the same users-and-roles screens for every product wastes months and makes every product behave a little differently. The core is written once and kept the same everywhere.

Decisions: why we never argue twice

Every choice that shapes a product is written down as a numbered decision, with the reason. When someone asks "why does it work like this?", the answer is a number.

#Two logs

  • P21: permissions are named Module.action (Tasks.create, Tickets.triage).
  • P49: every record page starts with a Back button.
  • P80: a module owns its files.

#The rules

  1. A product never re-opens a P. If the platform itself must change, that is a new P in the kit (with the prototype, rules and components updated in the same change), and every product gets it.
  2. A product decision that is new gets the next D number before it is built.
  3. If two documents disagree, stop and ask. Don't pick one quietly.
Tip. When you start on a product, read its D-log from the top. It is the fastest way to understand what the product is and why it looks the way it does.

Prototype first

Before any server or app code, a product is drawn as a clickable prototype: a single index.html that looks and behaves like the finished product, with fake data. People click through it, argue about it and agree on it. Changing a prototype costs minutes; changing built code costs days.

#Making one

  1. Copy the kit's prototype/ into the product's docs/design/prototype/.
  2. Edit src/product.js: the product's name, icon, domain and accent colour.
  3. Add the product's modules as new files, src/parts_<module>.js (Shelui Tasks: parts_tasks.js). Register their menu items, permissions, routes and links at the kit's extension points (the table in the kit README.md), and register each record type with defineModule so links and Back work.
  4. Remove the example product's modules (Fomu's forms, templates, builder, results).
  5. Run python3 src/assemble.py. It joins the parts into index.html.
  6. Open index.html in a browser. The Screens button at the bottom left jumps to every screen.
bash
cd docs/design/prototype
python3 src/assemble.py      # → index.html and the component docs

#Checking it

Every screen is checked at 1280px wide in light mode and 390px wide in dark mode, at least: no errors in the browser console, no sideways scrolling, nothing cut off. The kit's tools/prototype-shots/ takes the screenshots that later prove the real app matches.

Watch out. Write a D decision for every product choice you make while drawing (what a field means, who can see what, what happens on delete). The prototype shows the result; the decision keeps the reason.

#The phone app's prototype

A product with a phone app draws it separately in docs/design/prototype-phone/ (from the kit's prototype-phone/). It is drawn for a phone only, 360 to 430 pixels wide, with its own shell (bottom bar, sheets) and its own screens. It shares the data and the decisions with the web prototype, not its components.

#One module, one folder (P80)

The most important rule of the code: everything about one thing lives in one folder, under the same name on every side. To change how tasks work you open api/app/Modules/Custom/Work/Tasks/, web/src/modules/tasks/ and, on the phone, mobile/resources/spa/src/modules/tasks/; nothing about tasks is anywhere else. The file names say what they do: TasksCreateService.php creates a task, TasksDetailsPanel.vue is a task's details panel.

Why. In a large app most time goes into finding code. When the folder and the names are predictable, a new developer finds anything in seconds. PROJECT_GENERATOR proved this on many products; the kit made it the rule (P80).

Source: docs/guide/chapters/04-the-repository.md

The life of a module

A module is one kind of thing the product manages (Tasks, Tickets, Projects, Users). Every module goes through the same life, in the same order. Following the order is what keeps a product consistent.

#1. Idea and decision

Someone needs something ("developers need tickets"). It is discussed until the open questions are answered, and each answer becomes a D decision (what a ticket is, who raises it, what its statuses are, who sees it).

#2. Prototype

The module's screens are drawn in the prototype (chapter 3): its list, its details page and tabs, its form, its actions, its empty and error states, on a desktop and on a phone. The screens are clicked through and agreed.

#3. Data

The module's tables go into the product's ERD: columns, types, which columns point at other tables (foreign keys), what happens to children when a parent is deleted, which statuses a record moves through. Real foreign keys are always declared in the database.

#4. Plan

The module's work is added to docs/IMPLEMENTATION_PLAN.md as numbered steps (chapter 10), and a row per step to docs/PROGRESS.md.

#5. The API side

In this order, in api/app/Modules/{Tier}/{Group}/{Module}/:

  1. module.json: the module's manifest (its key, label field, references, permissions, actions, child tabs, menu entry). See docs/architecture/MODULES.md.
  2. Migrations/: the tables, with foreign keys.
  3. {Module}Model.php and {Module}Factory.php.
  4. Services/: one class per operation (list, view, create, edit, delete, delete check, splash, activity), then Actions/ for its actions.
  5. Routes/api.php and {Module}Controller.php: one route per operation, each behind its permission.
  6. Seeders/: the module's permissions and its menu row.
  7. Tests/: services, permissions, scoping, and the convention tests pass.

Nothing is registered by hand: the module provider finds the folder (P82).

#6. The web side

In web/src/modules/{module}/:

  1. module.ts: defineModule({...}), the same key and permissions as the API's manifest.
  2. routes.ts, then the pages: the list, the details layout, the overview, the tabs.
  3. components/: the form dialog, the details panel, the preview (what a link to this module opens), action dialogs.
  4. locales/en.json and sw.json.
  5. tests/: unit tests and the visual test that compares each screen with the prototype's screenshot.

#7. The phone side (if the phone shows it)

In mobile/resources/spa/src/modules/{module}/: its own module.ts (the same key and permissions as the API), its screens and sheets drawn from the phone prototype, its composables, locales and tests. It reuses only packages/shared (the API client and types, statuses, formatters), never the web module's pages or components (P93).

#8. Explain it

The build guide gets the chapter that explains how this module was built (its data, its files, its commands, its checks), the plan step is corrected if the work differed, and the tracker row is marked done with how it was verified (P92). Then the pull request is opened.

#9. Review and release

The pull request is reviewed against the prototype, the rules checklist and the definition of done, merged, and released (chapter 11).

#Changing a module later

A change goes through the same steps, smaller: a decision (new D or amended), the prototype, the data (a new migration, never an edited old one), the plan step and tracker row, the code on each side, the guide chapter, review, release.

#Switching a module off or retiring it

Set "enabled": false in its manifest: its routes, menu entry and pickers disappear, its tables and data stay. Removing it for good is a planned step of its own: a decision, a migration that archives or drops its tables, the folder deleted on every side, the guide chapter updated to say why.

Source: docs/guide/chapters/05-module-life-cycle.md

Tutorial: build one module end to end

We build a small Tasks module: a task has a title, an optional parent task (so tasks nest), an optional assignee, a status and a due date. Follow the steps in order. Each step ends with a check.

Note. The names below (BaseService, defineModule, ListCard, useList, RecordLink) are built in Phase 0 of every product from the kit's rules and component library. If you are in Phase 0, build them first (chapter 10, plan steps 0.x).

#Step 1: the manifest

api/app/Modules/Custom/Work/Tasks/module.json says what the module is. Everything else reads it.

json
{
  "key": "Tasks", "tier": "Custom", "group": "Work", "enabled": true,
  "label": "title",
  "references": {
    "parent_id":   { "module": "Tasks", "label": "title" },
    "assignee_id": { "module": "Users", "label": "name" }
  },
  "permissions": ["Tasks.setStatus"],
  "actions": { "setStatus": { "service": "TasksSetStatusService", "permission": "Tasks.setStatus", "button": "header", "opens": "menu", "bulk": true } },
  "children": { "subtasks": { "module": "Tasks", "via": "parent_id", "tab": "Subtasks" } },
  "menu": { "group": "Work", "label": "Tasks", "icon": "ListChecks", "order": 10, "permission": "Tasks.list" }
}

Check: php artisan modules:check lists Tasks with no errors (the manifest is valid; its references point at modules that exist).

#Step 2: the table

Migrations/2026_11_10_000001_create_tasks_table.php:

php
Schema::create('tasks', function (Blueprint $t) {
    $t->id();
    $t->ulid('uuid')->unique();
    $t->foreignId('organization_id')->constrained()->cascadeOnDelete();
    $t->foreignId('parent_id')->nullable()->constrained('tasks')->cascadeOnDelete();   // a subtask goes with its parent
    $t->foreignId('assignee_id')->nullable()->constrained('users')->nullOnDelete();
    $t->string('title', 200);
    $t->string('status', 20)->default('todo');
    $t->date('due_date')->nullable();
    $t->unsignedInteger('version')->default(1);                                          // P88: a stale save gets 409
    $t->foreignId('created_by')->constrained('users');
    $t->timestamps(); $t->softDeletes();
});
Why. The foreign keys are real (constrained()), so the database itself refuses a task whose parent does not exist, and deleting a parent removes its subtasks. Never rely only on code for this.

Check: php artisan migrate runs; php artisan migrate:rollback --step=1 and migrate again run too.

#Step 3: the model

php
final class TasksModel extends BaseModel
{
    protected $table = 'tasks';
    protected $casts = ['due_date' => 'date'];
    public function parent()   { return $this->belongsTo(self::class, 'parent_id')->withTrashed(); }
    public function children() { return $this->hasMany(self::class, 'parent_id'); }
    public function assignee() { return $this->belongsTo(UsersModel::class, 'assignee_id')->withTrashed(); }
}

There is no $fillable: only validated data ever reaches the model (P83), so the validation rules are the one list of what can be written.

#Step 4: the services

One class per operation. Services/TasksCreateService.php:

php
final class TasksCreateService extends BaseService
{
    public function __construct(private Notifier $notify) {}

    protected function rules(array $data): array
    {
        return [
            'title'       => ['required', 'string', 'max:200'],
            'parent_id'   => ['nullable', Rule::exists('tasks', 'id')->where('organization_id', $this->org())],
            'assignee_id' => ['nullable', 'exists:users,id'],
            'due_date'    => ['nullable', 'date'],
        ];
    }

    protected function process(array $valid): array
    {
        $task = TasksModel::create($valid + ['organization_id' => $this->org(), 'created_by' => $this->user()->id]);
        if ($task->assignee_id) $this->notify->send('task.assigned', $task);
        return $this->ok($task, 201);
    }
}

BaseService::execute() validates, then calls process() with only the validated keys, inside a database transaction. Write the others the same way: TasksListService (uses the list contract, P87), TasksViewService, TasksEditService (checks version, answers 409 when it is stale), TasksDeleteCheckService (counts the subtasks that would go), TasksDeleteService, and the action Actions/TasksSetStatusService.php.

#Step 5: routes and controller

Routes/api.php:

php
Route::prefix('tasks')->controller(TasksController::class)->group(function () {
    Route::get('list', 'list')->middleware('permission:Tasks.list');
    Route::get('create/splash', 'createSplash')->middleware('permission:Tasks.create');
    Route::post('create', 'create')->middleware('permission:Tasks.create');
    Route::get('{uuid}/view', 'view')->middleware('permission:Tasks.view');
    Route::put('{uuid}/edit', 'edit')->middleware('permission:Tasks.edit');
    Route::get('{uuid}/delete/check', 'deleteCheck')->middleware('permission:Tasks.delete');
    Route::delete('{uuid}/delete', 'delete')->middleware('permission:Tasks.delete');
    Route::get('{uuid}/activity', 'activity')->middleware('permission:Tasks.view');
    Route::post('{uuid}/set-status', 'setStatus')->middleware('permission:Tasks.setStatus');

The controller only hands each request to its service: return $this->respond(app(TasksCreateService::class)->execute($request->all()));

Check: php artisan route:list --path=api/tasks shows every route with its permission.

#Step 6: permissions and menu

Seeders/TasksSeeder.php upserts Tasks.list, view, create, edit, delete, bulkAction and the manifest's Tasks.setStatus, and the menu row from the manifest. Run php artisan db:seed.

#Step 7: API tests

Lists, details pages, forms and links

Every screen of a product is one of a few shapes. Each shape is decided once (the P decisions) and built from the component library, so every product feels the same.

#Lists (P24, P39, P40, P87)

  • One ListCard per list: toolbar (Refresh, Filters, Sort, then New on the right), quick tabs, search, filter chips, the rows.
  • Rows are ListRows with priority columns: as the card gets narrower, the least important columns fold into the line under the title, so nothing ever scrolls sideways.
  • Search, filters, sort and the page are in the address, so a copied link opens the same view.
  • The API side is the list contract: filters as { operator, value } on allowlisted fields, allowlisted sorts, at most 100 per page, bulk actions, export.

#Details pages (P26, P49)

  • A breadcrumb that starts with Back, a header (icon, title, code, status), action buttons (Refresh, Edit, the main action, More).
  • Tabs, with the active tab in the address: Overview first, History last. A tab that shows other records is that module's own list, locked to this record (P86).
  • Delete checks what would go with it, then asks you to type YES.

#Forms (P26, P42)

  • Create and edit open as one dialog. Every form keeps a draft on the server as you type, and offers it back if you leave and return.
  • No browser-native pickers: dates, times, files and selects use the library's pickers. Required fields have an asterisk.

#Links between records (P85)

Anywhere a record points at another (a task's project, a request's location), it is a RecordLink:

  • a click opens the other record's preview in a side sheet, with View full page;
  • Ctrl-click or middle-click opens it in a new tab;
  • if you may not open it, it is plain text with a lock and the reason;
  • a deleted record shows its label struck through; a missing one says so.
Tip. Open the kit prototype, go to Approvals, open a request and click its location. That is a RecordLink (the Design system page shows all its states).

Source: docs/guide/chapters/07-lists-details-forms.md

The phone app

A product's phone app is its own app, crafted for a phone only (360 to 430 pixels wide), the way Hodie is (P93). It is not the web app squeezed or rebuilt. It talks to the same API and follows the same rules for data, permissions and modules; it has its own shell, components and screens, and its own small Laravel inside the app for the phone's own work.

mobile/
  app/Http/Controllers/Native/   insets, keyboard, Back, files, camera, voice, alarms, updates, drafts, app log
  routes/web.php  routes/api.php the interface for every path · /api/native/*, /api/drafts, /api/cache
  resources/spa/src/
    app/                         start-up, session, the phone's behaviour, the frame (bars, drawer, sheets)
    components/                  the phone kit's pieces
    modules/{module}/            module.ts, screens/, sheets/, locales/, tests/
  scripts/build-web.sh           builds resources/spa into public/spa

#What is the same as the web

  • The modules: mobile/resources/spa/src/modules/{module}/, under the same names as the API and web modules, only for the modules the phone shows.
  • Shared code: only packages/shared (talking to the API and its types, permission names, statuses, formatting). Never the web app's screens or components. A phone usually shows fewer modules (Shelui Tasks: my work, tasks, tickets, alerts).
  • Links: a RecordLink on the phone opens a bottom sheet.
  • Strict TypeScript, the convention tests, the plan, tracker and guide.

#What is the phone's own (P51 to P79)

  • A phone moves. The app keeps the person signed in without a signal, saves the open form when it goes to the background, comes back where it was after Android closes it, never repeats a save it is unsure about, and shows "No connection" honestly.
  • The keyboard. On some phones the screen does not shrink when the keyboard opens; sheets lift by the keyboard's height (P71).
  • The Back key closes the top layer first (a sheet, a dialog, the menu), then goes back, then asks twice before leaving.
  • Updates come from a download page; the app checks, downloads, verifies and installs (P79).
  • The app log records what went wrong on a real phone so it can be followed up (P72).

Read docs/mobile/PHONE_MODEL.md (what a phone is, how it moves) and draw the phone prototype before writing phone code.

#The convention tests

They keep the rules true as the product grows: every manifest is valid and the API and web agree; every module has a menu entry and a label field; every reference points at a real module; every form has drafts; no module imports another module's pages or services; services write only validated data; list endpoints don't run a query per row.

Watch out. A failing convention test is never "fixed" by loosening the test. It means the code broke a platform rule; fix the code, or propose a new P.

Releasing and running

#A release

  1. Every phase ends with its pull request merged and its definition of done ticked.
  2. The version is raised (the API, the web app, and the phone app's version name and integer version code).
  3. The API is deployed with its migrations; the web app is built and deployed.
  4. The phone app is built signed (the key lives outside the repository), its file is checked (SHA-256), and the download page's latest.json is updated; phones update themselves (P79).
  5. The release notes go in the guide's "Releases" page.

#Running it

  • Secrets never go in the repository: .env files stay on the servers; only .env.example is committed.
  • Logs: the API's logs and the phone app's log (exported by the person when something goes wrong).
  • Backups of the database are the server's job, tested by restoring one.
Note. Each product's guide writes down its own servers, addresses and steps in this chapter. The kit cannot know them.
