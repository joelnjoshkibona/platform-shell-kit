# Proposal: P94–P98 (kit 1.14.0)

Status: **P95, P96, P97 and P98 are decided and built** (kit 1.15.0–1.17.0; see their specs in `docs/platform/`); P94 is next. This was the proposal, for the owner's review. Once agreed, each part becomes a decision row and spec, the prototype draws its screens, and the rules, components and guides are updated together, as with every P.

The owner asked for (2026-11-07):
- starter projects: API only, web only, mobile only;
- background work: an export or a report runs in the queue and comes back later as a notification with a details page;
- reports redesigned: paged or not, totals and aggregates, columns chosen by the person with fixed headers and columns, a chart builder with chosen axes, downloads;
- logs, queue, scheduled tasks, trash, notifications and permissions as real screens;
- a user guide for the people using the product: how to do each task, with screenshots marked ①②③ and text explaining each mark;
- broadcasts folded into notifications.

Sources: SYSTEM_SHELL already has much of the backend:
- `app/Project/Logs` (activity, error, login and request logs);
- `app/Project/Queue`, `app/Project/ScheduledTasks`;
- `Modules/Core/Reports` (with `GenerateReportJob`);
- `Modules/Core/Notifications` (with Broadcasts, actions, mappings and subscriptions);
- `Modules/Core/Trash`.

Its frontend has pages for logs, queue, reports, scheduled tasks and notification settings. The kit takes these and designs their screens to the kit's rules.

## P94 · Starter projects

**Problem.** Every product starts by copying the kit's templates by hand, and a product that needs only a part (an API for a partner, a web app over an existing API, a phone app on its own) has no starting point.

**Proposal.**
- `starters/` in the kit holds four runnable skeletons, each passing its own checks on day one:

| Starter | What you get | Data lives |
| --- | --- | --- |
| `full` | `api/` + `web/` + `packages/shared/` + `docs/` + `tools/` (+ optional `mobile/`) | the API |
| `api` | `api/` with the module loader, base services, list contract, tenancy, convention tests and one example module; `docs/`; `tools/guide` | the API |
| `web` | `web/` with the shell and the component library, `packages/shared`, pointed at an existing platform API by URL | an existing API |
| `mobile` | `mobile/` in Hodie's shape (P93). Two flavours: **connected** (talks to an existing platform API) or **on the phone** (its own Laravel is the backend, data in the phone's SQLite, as Hodie) | the API, or the phone |

- One command creates a product from them:

```bash
php tools/new-product.php      # or: node tools/new-product.mjs
  ? Product name          Shelui Tasks
  ? Parts                 [x] api  [x] web  [x] mobile (connected)
  ? Domain, app id, accent ...
  → shelui-tasks/ with the parts, the placeholders filled, docs/ (decision log, plan, tracker, build guide, user guide), git init, first commit
```

- Every starter carries the deliverables (P91, P92): the implementation plan, the tracker, the build guide skeleton and the user guide skeleton (P98).
- **CI in the kit** builds each starter on every kit change (install, type-check, tests, guide check), so a starter can never rot.

**To draw:** nothing. **To write:** `starters/`, `tools/new-product`, guide chapter "Starting a product".

## P95 · Background work and its results

**Problem.** Exports, reports, imports and large bulk actions take time. Today the person waits on a spinner, or the work dies with the request.

**Proposal.**
- **Anything that may take more than a few seconds runs as a job:** export, report run, import, bulk action, a heavy recalculation. The button says what will happen ("We'll let you know when it's ready") and the person keeps working.
- **One record per run:** a job run with its kind, who started it, the parameters (module, filters, columns, format), status (waiting, running, done, failed, cancelled), progress, a result (file, row count, summary), errors, started and finished times, and when the result expires.
- **Done or failed sends a notification** (in the app, and by email or push if the person wants) that opens the **job page**:
  - what was asked;
  - progress;
  - the result, with Download, a preview of the first rows and the row count;
  - errors in plain words (for an import, row by row);
  - **Run again** with the same settings, and Cancel while it runs.
- **My jobs**: each person's list of runs, under the avatar menu. Admins see everyone's in **Queue** (P97).
- Result files are private and expire, 7 days by default and set in Settings. Expired runs keep their page and say "The file expired; run it again".
- Exports behind an approval (P18) start their job only once approved.

**Data.** `job_runs` (id, ulid, organization_id, user_id, kind, module, params JSON, status, progress, result_media_id, rows, summary JSON, errors JSON, started_at, finished_at, expires_at). This sits on top of Laravel's own `jobs` and `failed_jobs`.

**API.** `POST /{module}/export` (and `/reports/{id}/run`, `/import`) answers 202 with the run. `GET /job-runs/list`, `/job-runs/{uuid}/view`, `/download`, `/rerun`, `/cancel`.

**To draw:** the "started" toast, the notification, the job page (running, done, failed, expired), My jobs. **Components:** `JobProgress`, `JobResult`.

## P96 · Reports and the chart builder

**Problem.** Reports today are fixed pages. People want to shape the numbers themselves: which columns, which totals, which chart, and to take the result away.

**Proposal.**
- **A report** is a definition on top of a module's data. Its source is a module's list endpoint, or a report service for joins and calculations. It has its own fields (label, type, whether a field can be grouped, summed or averaged) and default filters. Products ship reports; admins can make more.
- **The report viewer**:
  - the list contract's filters (P87), with a date range always to hand;
  - **paged or all rows** ("All" is limited by a setting; above the limit it offers to export instead);
  - **columns the person chooses**: show, hide, reorder by dragging, resize, and **pin** to the left;
  - **the header row and pinned columns stay fixed** while the table scrolls both ways (a report table is not a ListCard: P40 already says report tables may scroll);
  - **totals, two ways** (owner, 2026-11-07):
    - a **footer row** under the columns: sum, average, count, min or max, chosen per number column;
    - an **aggregate strip at the top**, switched on or off, showing the totals for **everything the page's filters match, whatever page you are on**.
    - Both are computed **by the server** (`GET /reports/{id}/aggregate` with the same filters). The browser only holds the page it shows, so it cannot total the rest.
  - **group by** one or two columns with subtotals, folding and unfolding; the subtotals are computed by the server too.
  - **the header must stick**: checked by a test that scrolls a long report and asserts the header row and the pinned columns stay on screen, on desktop and phone.
- **The chart builder**, a panel beside the table, built on **Highcharts only** (owner):
  - chart types: bar, stacked bar, line, area, pie or donut, scatter, KPI number;
  - **X axis**: any groupable field (dates by day, week, month or year);
  - **Y**: one or more measures, each with its aggregate (sum, average, count, min, max);
  - **series**: split by a second field;
  - options: labels, legend, sort, top N with "Other";
  - a live preview on the report's current filters;
  - save the chart with the view; several charts per report;
  - charts follow the kit's chart palette in light and dark.
- **Saved views**: filters, columns, pins, grouping, totals and charts, saved **just for me** or **shared** (by role or location), with one marked as the default.
- **Exports, a first-class part of every report** (owner):
  - the **table** as Excel, CSV or PDF, with the view's filters, columns, order, grouping and totals. These are made **by the server**, over every matching row, as background jobs (P95), so a large report never freezes the page.
  - a **chart** as PNG, SVG or PDF, and its data as CSV. These are made **in the browser** by Highcharts' offline exporting module; no export server is needed.
- **Scheduling (later, optional)**: email a saved view every Monday, using scheduled tasks (P97) and background jobs (P95).

**Data.** `reports` (key, module, name, description, source, fields JSON, default filters), `report_views` (report_id, owner_id, shared_with JSON, filters, columns, pins, group_by, totals, charts JSON, is_default).

**To draw:** the Reports list, the report viewer (table, fixed header and columns, totals, grouping), the column chooser, the chart builder (empty, building, saved), saved views, the download menu, phone width (the table becomes cards with the totals on top; the charts stack).

**Components:** `ReportTable`, `ColumnChooser`, `ChartBuilder`, `Chart`, `SavedViews`.

**Chart library: Highcharts, and nothing else** (owner). It is loaded only on pages with a chart, uses the kit's tokens for light and dark, and its accessibility module is on.

> **Watch out**: Highcharts is free for non-commercial use only. A product run for a customer needs a Highcharts licence (per developer or per product). Each product records its licence in its decision log before Phase 0.

## P97 · The system screens

Designed in the prototype from SYSTEM_SHELL's backend and pages, all as kit list and details pages (P24, P26, P40). They are core modules every product gets.

| Screen | What it shows | Actions | Permission |
| --- | --- | --- | --- |
| **Logs** | Tabs: **Activity** (who did what to which record, before → after, the same entries as each record's History tab), **Sign-ins** (when, from where, device, failed attempts), **Errors** (the application error log, grouped by kind with a count), **Requests** (slow or failed API calls, for admins) | filter, open the record (RecordLink), export (P95) | `Logs.list` |
| **Queue** | Jobs waiting, running, done, failed; job runs of every person (P95); the failed ones with their error | retry, cancel, delete, open the job page | `Queue.list`, `Queue.manage` |
| **Scheduled tasks** | Every cron task: what it does in plain words, how often, last run (result, duration), next run, enabled | Run now, pause or resume, the run history | `ScheduledTasks.list`, `ScheduledTasks.manage` |
| **Trash** | Deleted records of every module, who deleted them and when, the days left before they go for good (30 days by default); a record's dependants are shown with it (a task with its subtasks) | restore (with its dependants), delete for good (type YES), empty trash | `Trash.list`, `Trash.restore`, `Trash.purge` |
| **Notifications** | **Inbox** (mine), **Settings** (mine: channels per kind, quiet hours, P36), admin **Rules** (which event notifies whom by which channel; the old notification actions, mappings and subscriptions in one screen), **Announcements** (send one message to people chosen by role or location, now or scheduled, in the app or by email, SMS or push; this replaces Broadcasts) | send, schedule, cancel an announcement; edit rules | `Notifications.list`, `Notifications.manage`, `Notifications.announce` |
| **Permissions** | Every permission by module, in words; which roles grant it; which people have it (directly or through a role, at which locations) | open a role or a person; view as (P10) | `Permissions.list` |

**To draw:** each list and details page, with empty, loading and error states, in light and dark, at desktop and phone width.

## P98 · The user guide (for the people using the product)

**Problem.** People learn the product by asking someone. Nothing tells them, step by step, how to raise a ticket or triage one.

**Proposal.**
- **One article per task** a person does ("Raise a ticket", "Triage a ticket into tasks", "Move a task under another one", "Export your tasks"), grouped by module, with: what it is for, who can do it (the permission in words), the steps, what happens next, and related articles.
- **Numbered screenshots**: each step that shows a screen has a screenshot with markers ①②③ placed on the exact buttons and fields. The text refers to them: "Tap **Triage** ①, choose the owner ②, …".
- **Written as Markdown with a small marker spec**, for example:

```markdown
## Triage a ticket into tasks
::: shot route=ticket:TCK-1 width=1280 theme=light
1 = button:has-text("Triage")       Open the triage dialog
2 = [aria-label="Owner"]            Choose who owns it
3 = button:has-text("Create tasks") Create the tasks
:::
```

- The screenshot tool (`tools/prototype-shots`, then the real app's Playwright) opens the screen, finds each element, draws the numbered markers, and saves the picture. Desktop and phone shots come from the same spec.
- **Kept true by a test:** a marker whose element no longer exists fails the build, and screenshots are re-taken whenever their screen changes.
- **Where it shows:**
  - in the app: **Help and guides** (the link already in the sidebar) with search, and a "How do I…" link on each screen opening the articles about that screen;
  - and as an HTML page (built like the build guide, P91) to share or print.
- Every product keeps `docs/help/` (articles in English and Swahili), and every pull request that changes a screen updates its articles (added to P92's check).

**To draw:** Help and guides (search, by module), an article with marked screenshots, the "How do I…" link on a screen. **Tools:** `tools/help/` (spec → marked screenshots → in-app JSON + HTML).
