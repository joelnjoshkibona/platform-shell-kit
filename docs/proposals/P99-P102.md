# Proposal: P99–P102, and P94 rescoped (kit 1.17.0)

Status: **proposal, for the owner's review**. Nothing here is built or drawn yet. When a part is agreed, it becomes a decision row and spec, the prototype draws its screens, and the rules, components and both guides are updated together, as with P95–P98.

The owner asked for this on 2026-11-07, when choosing how to build the starters:

> "Should we make sure our list pages also have a full search too, are we able to toggle batch actions on a list? Do we have a view on how tabs will be navigable or ability to open a modal and pass some parameters that might hide, disable or prefill a field in a form? Also we have a full structure of how we want our backend to be, then we adhere to that on the starter kit and ensure all features, home page, auth (login and reset), logs, queues, etc. work end to end. … we have offline version and api version. We can also have a sync version."
>
> "I think we need to make the platform kit generic as possible so that it fits all our needs whenever they come across."

Then: a written proposal first; the phone app gets all three data modes (connected, on the phone, sync); the build is several pull requests, each merged before the next.

## P99 · Select mode and batch actions on lists

**Problem.** People can act on one record at a time only. The API can already do an action on many records, but no screen lets a person choose them.

**Proposal.** (Owner, 2026-11-07: "I don't want checkboxes to show up immediately; rather a batch mode toggle, then we begin our batch actions, taking care of the selected page or all based on the filters.")
- **Batch mode is off by default.** A list looks exactly as it does today: no tick boxes, nothing extra.
- **A Batch button** in the list toolbar, after Sort, turns batch mode on. It shows only when the module has at least one bulk action the person may use.
- **In batch mode:**
  - a tick box appears at the start of each row, and the toolbar is replaced by **the batch bar**;
  - the person chooses **what** the action applies to:
    - **Ticked rows**: tick rows one by one, or **Tick this page** (the rows on the screen now);
    - **All that match**: "**All 340 that match these filters**", every row the current filters, search and tab match, on every page;
  - the bar always says which it is, and how many: "12 ticked" or "All 340 that match";
  - the bulk actions from the module's manifest (`actions` with `bulk: true`) sit on the bar, with the most used first and the rest under **More**;
  - on a phone, the bar sits at the bottom, above the safe area (P62). Long-pressing a row also turns batch mode on, with that row ticked.
- **Done**, or Esc, leaves batch mode and clears the ticks.
- **"All that match" is sent as the filter, not as ids** (`mode: filter`), so it is exact even for thousands of rows. Rows added after the click are not included: the server fixes the set when the action starts.
- **Safety:**
  - an action that deletes or cannot be undone asks first, saying how many it affects;
  - deleting many records needs **YES** typed, as for one (P26);
  - an action behind an approval (P18) makes one request for the whole batch.
- **Size:** up to 100 rows are done straight away. Above that, or when "all that match" is chosen, the batch runs as a background job (P95), with its own page and notification.
- **The result is shown per row:** "38 done, 2 skipped". **Skipped** opens the list of skipped rows with the reason for each ("already closed", "you can't edit Arusha's records"). Rows that were done stay selected until the list refreshes, so the person can see what happened.
- **Changing the filters, the search or the tab while ticking clears the ticks**, with a toast if anything was ticked, so the person never acts on rows they no longer see. With **All that match**, the count simply follows the new filters. Leaving the list ends batch mode.
- **Selecting is never part of the link.**
- A list inside a tab (P39) works the same way, scoped to its parent.

**API.** `POST /{module}/bulk-action` with:

```json
{ "action": "close", "mode": "ids", "ids": [] }
{ "action": "close", "mode": "filter", "filters": {} }
```

It answers `200 { done, skipped: [{ uuid, label, reason }] }`, or `202` with a job run (P95).

**To draw:** the toolbar with Batch; batch mode on desktop and on a phone (ticked rows, Tick this page, All that match); the confirm dialog; the result with the skipped rows; a batch that becomes a job.

**Components:** `useBatch` (on or off; ticked ids or the filter; count), `BatchBar`; `ListRows` gets `selectable`, shown only in batch mode.

**Open:** should a few actions be allowed on a mixed selection (for example, Assign) while others (Close) skip the rows they can't apply to? Proposed: yes, and they are reported as skipped.

## P100 · Opening a form with settings (form context)

**Problem.** A form is opened from many places: a list's New button, a tab ("New task in this project"), an action ("Reassign"), a notification ("Do it now"). Each place needs some fields already filled, some fixed, some hidden. Today only the tab case exists (LockedField), and it is not enforced by the server.

**Proposal.**
- Any screen can open any module's create or edit form with a **form context**:

| Setting | What the person sees | Example |
| --- | --- | --- |
| `prefill` | the field is filled, and can be changed | due date = tomorrow |
| `lock` | the field is shown with its value and a lock, and cannot be changed (today's LockedField) | Project = Website |
| `hide` | the field is not shown; its value is fixed | `source = ticket` |
| `disable` | the field is shown greyed, with the reason on hover or tap | "Priority is set by the ticket" |
| `title` | the dialog's title | "New task for TCK-12" |
| `after` | what happens after Save: `stay` (another), `open` (the new record), `back` (where you came from) | `open` |

- **One way to open it**, from code: `openForm('tasks', { mode: 'create', prefill, lock, hide, disable, title, after })`. A button, an action in a manifest, or a notification can carry the same object.
- **It travels in the link**, as `?form=tasks.create&prefill[project]=…&lock=project`. A reload, Back or a copied link opens the same form with the same settings, over the same page. Drafts (P26) remember the context.
- **The server enforces it**:
  - the screen asks the module's **CreateSplash** or **EditSplash** (P83) with the context;
  - the API answers with the form's fields and which are locked, hidden or disabled. It checks that the person may use the context: a lock to a project the person cannot see is refused;
  - on save, a locked or hidden field sent with any other value gets **422**;
  - so a context cannot be changed by editing the link.
- **The scoped create from a tab (P39) becomes one case** of this: `lock: { parent }`.
- **Actions in the manifest (P84)** may declare `opens: dialog` with a `form` and its context. "Reassign" is the edit form with only the owner field shown (`hide` all the others), and `title: "Reassign"`.

- **Dialogs and their buttons** (owner, 2026-11-07). The footer is fixed and laid out the same way in every dialog:

```
Viewing another record's tab:   [Close]                                  [Open full page →]
A form:                         [Close]  Draft saved 12:41                            [Save]
A form with a workflow:         [Close]  Draft saved 12:41      [Save as draft]     [Submit]
```

  - **Close** is always on the left. The main action is always furthest right, with the second action next to it.
  - **A dialog closes only through its footer**: there is no × in the corner, and clicking outside does nothing, so nobody loses work by clicking the wrong place.
  - **Esc** and the phone's **Back** button (P61) count as pressing Close.
- **Drafts stay exactly as decided (P26, the generator's drafts logic):**
  - a server draft is saved about every 4 seconds while typing;
  - create forms keep several drafts, with a picker; edit forms keep one per record, with Restore or Discard;
  - **My drafts** in the account menu lists them all;
  - never files or secrets, and never in step-by-step action wizards.
- **Closing a changed form saves its draft at once** (owner, 2026-11-07: "any close of a form that has changes needs to auto save to draft immediately"):
  - this covers Close, Esc, Back, leaving the page, signing out and the app going to the background;
  - the draft is saved immediately, not on the next 4-second autosave;
  - the form closes once the draft is saved, with a toast "Kept as a draft" and **Discard**;
  - if the draft cannot be saved (no signal, server error), the form stays open with "Couldn't save the draft", and **Try again** or **Close without saving**;
  - a form changed back to how it started has no draft, so it closes at once.
- **Two kinds of "draft", kept apart:**
  - **the autosaved draft (P26)** is a person's unfinished typing, seen only by them. It has no button: it saves itself.
  - **a record saved as Draft** is a real record with the status Draft (P47), which others may see and which is submitted later. It has a **Save as draft** button next to **Submit**, only on forms whose module has such a workflow.
- **Dialogs stack, and close one by one** (owner, 2026-11-07: "we should be able to stack multiple dialogs … and close them one by one"):
  - anything opened from inside a dialog opens **on top of it**: a form, another record's tab (P101), a record preview, a confirm. There is no fixed limit; a person can go as deep as they need;
  - each dialog in the stack sits slightly lower and narrower than the one below, so the stack shows. The top dialog's header has a short trail of the dialogs below ("TCK-12 › Website · Tasks › New task"); tapping an earlier step closes the ones above it, one by one, each saving its draft if changed;
  - **Close, Esc and Back close only the top dialog.** The one below is shown again as it was, refreshed if the dialog above saved something;
  - **Open full page** in any dialog closes the whole stack, top first, saving drafts as it goes, then goes to the page;
  - the stack is in the link (`?open=` lists each dialog in order), so a reload or a copied link opens the same stack.
- **Full screen** (owner, 2026-11-07): every dialog has a **Full screen** button in its header (an expand icon). Full screen fills the window, keeping the dialog's fixed header and footer; the same button returns it to its normal size.
  - The person's choice is remembered per kind of dialog (for example, "Tasks forms open full screen"), on their account, so it follows them to another computer.
  - On a phone every dialog is already full screen, so the button is not shown.

**To draw:**
- a create form with a locked, a hidden and a disabled field (the lock and the reason shown);
- a changed form closed with Close, Esc or Back ("Kept as a draft"), and the case where the draft can't be saved;
- three dialogs stacked (a tab, a preview, a form), with the trail in the header; closing them one by one; a dialog in full screen;
- a workflow form with Save as draft and Submit;
- an action that opens a cut-down edit form;
- what happens when the link's context is refused (a toast, and the plain form opens).

**Components:** `FormContext` (type and helpers); `openForm()`; LockedField becomes part of the form's field wrapper.

## P101 · Tabs you can open from anywhere and move through

**Problem.** Tabs are in the link, but to see another record's tab you leave your page (from a ticket to the project, then its Tasks tab). Also, some screens have many tabs (a record with eight related lists), phones show only three or four, and keyboard users cannot move between them.

**Proposal.**
- **Keyboard**, following the WAI-ARIA tabs pattern:
  - ← and → move between tabs;
  - Home and End go to the first and last tab;
  - the tab opens when it gets focus;
  - Tab moves into the tab's content.
- **Too many tabs to fit:**
  - the tab strip scrolls sideways, with faded edges where more tabs are hidden;
  - the open tab always scrolls into view;
  - on a phone, a **More** button at the end lists every tab with its count.
- **Counts:** a tab that holds a list shows how many rows it has (P39). Counts load with the page and never move the tabs when they arrive.
- **Tabs the person may not see are never shown.** A link to one (`?tab=costs` without permission) opens the first tab instead, with a toast: "You can't see Costs on this record."
- **Open another record's tab without leaving your page** (owner, 2026-11-07): from a ticket, open Project Website's **Tasks** tab in a **dialog**:
  - **the header is fixed**: the record's name and module, the tab's name, and the record's other tabs to switch between;
  - **the middle scrolls**: the tab's content exactly as on the details page (its list with search, filters and batch mode, or its overview);
  - **the footer is fixed**: **Close** on the left, **Open full page** on the right. That goes to the details page on the same tab, and Back returns to where you were. The dialog closes only through these two buttons (or Esc, or the phone's Back button, which act as Close: P100), never with a × or by clicking outside;
  - anything opened from inside it (New task, Edit, an action, another record) opens on top of it as the next dialog in the stack, and after saving the tab below shows the change (P100);
  - it has the Full screen button like every dialog (P100);
  - on a phone the dialog fills the screen, with the same header and footer.
- **Any module can open it**:
  - `RecordLink` gets a `tab` setting (`<RecordLink module="Projects" :id tab="tasks">`);
  - actions, menu items and notifications can also point at a record's tab;
  - each module lists its tabs in its manifest (key, label, permission), so a wrong tab name fails the type check and a tab the person may not see is not offered.
- **The dialog is in the link** (`?open=projects/PRJ-7/tasks`), so a reload or Back keeps it, as the record preview does (P26).
- **Every tab has its own `?tab=`** (already P26). Inside a tab, its own list keeps its search and filters in the link too (P39).

**To draw:**
- another record's tab in a dialog, from a ticket (desktop and phone), and Open full page;
- a record with many tabs on a desktop (scrolling, fades) and on a phone (More);
- moving with the keyboard (focus ring);
- the toast for a tab you cannot see.

**Components:** `RecordTabDialog` (fixed header and footer, scrolling middle); `RecordLink` gains `tab`; `Tabs` gains `overflow` and keyboard support.

## P102 · The phone app's data modes: connected, on the phone, sync

**Problem.** P93 makes the phone app connected only: the API holds the data. Some products work where there is no signal for days; others, such as Hodie, have no server at all. The owner wants the kit to fit all of these.

**Proposal.**
- **One phone app, the same frame (P93), three data modes.** A product picks one when it is created (`tools/new-product`), and a module may override it in its `module.ts` (for example, a product that is connected, with a sync-mode field log).

| Mode | Where the truth is | Without signal | Example |
| --- | --- | --- | --- |
| **connected** | the API | read-only: the last data it saw, with its age (P57, P59); writes wait for signal | Shelui Tasks, DevBiz |
| **on the phone** | the phone's own Laravel and SQLite | everything works; there is no server | Hodie |
| **sync** | the API, with a full working copy on the phone | everything works; changes wait in a queue and are sent when the signal returns | field data collection, stock counts |

- **One data layer** with the same five calls in every mode:
  - `list(module, query)`
  - `view(module, id)`
  - `save(module, record, version)`
  - `delete(module, id)`
  - `action(module, name, ids, input)`

  It has three implementations: `remote` (the API), `local` (the phone's Laravel, through `/api/local/*`), and `sync` (local, plus the queue). **Screens and modules never know which mode is on.** They speak the same list contract (P87) in every mode, so a list page looks and filters the same way.
- **Sync, in detail:**
  - **IDs are ULIDs made on the phone**, so a record exists before the server hears of it.
  - **The queue** of changes waiting to be sent is a table in the phone's SQLite. Each change has a key the server remembers, so sending one twice does nothing the second time. This amends P60 **for this mode only**: a queued change *is* re-sent, safely, because the server ignores repeats. In connected mode, P60 stays as it is.
  - Changes are sent in the order they were made. A record's attachments go after the record.
  - **From the server:** `GET /sync/changes?since=<cursor>` returns what changed for this person's organisation and locations, in pages. Deletions are included.
  - **Conflicts:** every record carries `version`. If the server's copy changed since the phone's, the server answers **409 with its copy**. The phone keeps the person's version as a draft and shows both: **Keep mine** (send again with the new version) or **Use theirs**. Nothing is overwritten silently (as Shelui D32).
  - **What is copied to the phone** is set per module (for example, "my tasks and my locations' tasks for 90 days"), so the phone holds what the person works with, not the whole database.
  - **People see it:** a "Last synced 5 min ago · 3 changes waiting" line; a Sync now button; a list of changes that failed, with why.
  - **The queue survives** the app being closed or killed (P58). Signing out with changes waiting asks first: "3 changes have not been sent. Send now, or sign out and lose them?"
  - **Permissions** are checked again by the server when a change arrives. A change refused because the person lost access is shown in the failed list.
- **On the phone** (Hodie's way): the phone's Laravel holds the modules' own tables and services (P83), with the same list contract (P87). There is no server and no sign-in; backups and updates follow Hodie (export file, update check, P67).
- **Amends P93**: in the on-the-phone and sync modes, the embedded Laravel holds the product's data. Connected stays as P93 says.

**Data.**
- On the phone: `sync_queue` (ulid, module, op, record_id, payload, version, key, tries, error, created_at) and `sync_state` (module, cursor, last_synced_at).
- On the server: `sync_keys` (key, user_id, result, created_at), kept for 30 days.

**API.**
- `GET /sync/changes?since=`
- `POST /sync/push`: a batch of changes, each with its key; it answers per change with done, 409 with the server's copy, or refused.

**To draw:**
- the sync line and Sync now;
- the changes waiting list;
- the conflict screen (mine and theirs side by side);
- signing out with changes waiting;
- the first sync (downloading, with progress).

**Components:** `SyncStatus`, `ConflictSheet`; the data layer `data.ts` in the phone app's `src/app/`.

**Open:** should the web app have a sync mode as well (in a browser, using IndexedDB)? Proposed: **not now**. Web stays connected; the phone app covers people without signal.

## P94 rescoped · Starters that run the whole core, end to end

**Problem.** This replaces P94 in `P94-P98.md`. The owner wants each starter to follow the agreed structure (P80–P93) **and** to have every core feature working from day one, not a thin skeleton.

**Proposal.**
- **Built from DevBiz's core modules, reshaped into the kit's layout.** DevBiz is the newest and fullest copy of the shared base. The shop modules and `components/devbiz` are left out.
- **API** (`api/`, Laravel 13, PHP 8.4, Pest):
  - `app/Kernel/`:
    - Auth: sign-in by email, phone or username; password reset; two-step sign-in (TOTP) and trusted devices;
    - Tenancy (organisations, the global scope, `/{org}`);
    - Modules: the loader that finds each `module.json`, and `php artisan modules:check`;
    - Services: `BaseService` and `ListService`. `ListService` is ported from DevBiz's `ListServiceTrait`, about 1.7k lines, with its tests;
    - Logs, Queue, ScheduledTasks and Settings.
  - `app/Modules/Core/<Module>/` for every core module, each with its own `module.json`, routes, migrations, services (one per operation), actions and tests.
  - The convention tests (P90).
- **Web** (`web/`, Vue 3, Vite, strict TypeScript):
  - `src/app/` holds start-up, the module loader, the session, languages and the frame (sidebar, top bar, search, curtain);
  - `src/components/` holds the component library (from DevBiz's `ui/` and `app/`, matched to the prototype);
  - `src/modules/<module>/` holds every core screen of the prototype.
- **Works end to end, each with a test:**
  - signing in: sign-in, password reset, two-step sign-in, choosing an organisation;
  - home (the dashboard);
  - people and access: Users, Roles, Permissions, Locations, Settings, Menu management;
  - content: Media, Trash;
  - messages and approvals: Notifications with Announcements, Approvals;
  - drafts on every form, and My drafts (P26, the generator's drafts logic, ported with its API);
  - system: Logs, Queue, Scheduled tasks;
  - background jobs and their pages, Reports with the chart builder, Help and guides;
  - then P99–P101 once they are decided.
- **The starters**, in `starters/`:
  - `full`: api, web and shared, with mobile optional;
  - `api`;
  - `web`, pointed at an API by its address;
  - `mobile`, with its data mode (P102).

  Each carries the deliverables already filled in: the plan, the tracker, the build guide, and `docs/help` with the core articles.
- **One command:** `node tools/new-product.mjs` asks for the name, slug, parts, the phone's data mode, domain, app id and accent. It copies the parts, fills every placeholder, runs `git init` and makes the first commit.
- **Kit CI** (`.github/workflows/starters.yml`) runs on every kit change. For each starter it installs, type-checks, runs the tests, and runs the guide and help checks, so a starter can't go stale.
- **Built in this order, one pull request each, each verified and merged before the next:**
  1. The API kernel: auth, tenancy, the loader, BaseService and ListService, with their tests.
  2. The API core modules, with their tests and the convention tests.
  3. The web frame and the component library.
  4. The web core screens, end to end against the API (Playwright).
  5. `packages/shared`: the API client and generated types, permissions, statuses, formatting.
  6. The phone app's frame, connected mode.
  7. The phone app's on-the-phone and sync modes (P102).
  8. `tools/new-product`, the full starter, kit CI, and the docs: the guide chapter "Starting a product", templates, the skill and the README.

**Size and risk.** This is the largest change the kit has had. Each pull request moves code from DevBiz and reshapes it, with its tests moving with it. Shelui Tasks would be the first product made from the starters.

**Open:**
- **Which core modules may a product switch off?** Proposed: Approvals, Reports, Announcements and Menu management can be switched off (`enabled: false`). The rest are always on.
- **Approvals in every starter?** Proposed: yes, switched off by default.
- **Version pins:** Laravel 13, PHP 8.4, NativePHP mobile 4, Vue 3.5, Node 22.
