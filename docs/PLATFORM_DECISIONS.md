# Platform decisions (P-log)

> These are decided for every product on the platform. A product inherits them and never re-opens them; it keeps its own D-log for product decisions. Change a P only here, with a new P that supersedes it, then update the kit prototype, rules and components in the same commit. Each entry notes the Fomu decision it came from.

| P | Decision | Was | Detail |
| --- | --- | --- | --- |
| P1 | ID strategy | D4 | ULID for every record that appears in a URL or is shared outside the app; bigint for internal tables. |
| P2 | Admin sign-in | D7 | Email, phone or username + password, then TOTP 2FA (Fortify). Optional 30-day trusted device; org can require 2FA. |
| P3 | Roles and menu access | D8 | Cobley-style JSON roles (spatie removed). roles.permissions is a JSON array of permission names in Module.action form (Forms.list, Forms.create, Responses.export; see D28). One permission per child menu; parent visible if any child is (OR); empty parents hidden. Missing permissions go to a role first, to a single user (granted_permissions on user_locations) only as an exception. |
| P4 | Menus, selects and popovers never clip | D9 | Always use shadcn-vue *Content components (DropdownMenuContent, SelectContent, PopoverContent, TooltipContent) with their portal on and collisionPadding 8. Never position a menu with absolute inside a scrolling or overflow-hidden container (tables, card lists, dialog bodies). |
| P5 | Clickable cards with actions | D10 | A card that opens on click uses a stretched link; its action buttons (menus, toggles) sit above it with relative z-10 so they stay tappable. |
| P6 | Tables on phones | D11 | Below 640px every data table switches to a compact card list (forms list, responses, members). The table/cards toggle only applies from 640px up. |
| P7 | Server-side access matches the menu | D12 | Every route and API endpoint behind a menu checks the same permission (Laravel middleware can:<permission>). Hidden menu = 403 on direct visit, shown as a 'No access' page with a request button. |
| P8 | Page transitions | D13 | Curtain plays on first app load (starts closed with 'Loading…', opens once the app is ready; the closed curtain is in the server HTML so nothing flashes) and on every page change, sidebar navigation included (revised 10 Oct). Not between sign-in steps or between tabs inside a page. Loader appears only if the next page takes longer than 300ms. Skipped with prefers-reduced-motion and switchable off in the prototype. Curtain colour has its own tokens: bright teal (--curtain 170 62% 46%, dark text) in light mode, deep green (166 58% 13%, light text) in dark mode. |
| P9 | Sidebar menu animation | D14 | Animation follows the display mode by default (dropdown: expand + stagger, panel: slide, rail flyout: fade); per-menu override in Menu Management. Dropdowns are always accordion. Forms and Configuration cannot be hidden. |
| P10 | Menu Management layout | D16 | The page is information only: parent/child rows (drag to reorder, drag a child onto another parent to move it) showing type, permission, who sees it and status. | P11 | Design system reference | D17 | The prototype's Design system page is the source of truth for tokens (colour, type, spacing, radius, shadow, motion, z-index, breakpoints), the component inventory with sizes and variants, and layout rules. The build copies its values into tailwind.config and the shadcn-vue theme CSS; any change is made there first. |
| P12 | Shared platform core | D18 | Identity, organisations, roles, permissions, menus, statuses, locations, wards and approvals reuse the Cobley Platform core. Every tenant-owned core table gets organization_id; system rows (roles, location types, statuses) keep it NULL and are shared. |
| P13 | Main role vs location roles | D19 | One MAIN role per organisation member (organization_users.role_id, role_type = system: owner, admin, editor, viewer). Several CUSTOM roles per location in user_locations.roles (JSON array of role ids, role_type = custom). A main role can never be stored as a location role; validated on save. |
| P14 | Overrides stay JSON | D20 | granted_permissions / denied_permissions / roles stay JSON on user_locations. Mitigations: MySQL 8 multi-valued indexes (CAST(... AS CHAR(80) ARRAY)) for 'who has X' queries, a FormRequest rule that every value exists in permissions.name, every change written to the activity log with before/after, and a migration that renames values when a permission is renamed. |
| P15 | Effective permission rule | D21 | At a location: main role permissions UNION custom-role permissions at that location and every ancestor (via location_closures) UNION granted_permissions, MINUS denied_permissions. Deny always wins. Result cached per user + location, busted when any input changes. |
| P16 | Statuses | D22 | Master-data status (users, organisations, locations, roles, request types) uses the statuses table (status_id). Workflow states: see P47 (one lookup table per workflow, fixed codes). |
| P17 | View as | D24 | Admins with Users.impersonate can preview the app as another user or as a role (D37): read-only, a banner shows who is being viewed, no writes, no OTP or emails. Each session is recorded in impersonation_sessions (who, whom, location, started, ended). |
| P18 | Approvals are core | D25 | The Cobley approval engine (request_types, steps with role/permission/user approvers and or/and combinators, requests, request_approvals, delegations) is part of the core. First request types: Publish form, Export responses, Reset respondent. Approvers are resolved at the request's location and its ancestors. |
| P19 | Locations screens | D26 | List is a tree table (expand/collapse, search keeps matching rows with their ancestors) that becomes an indented card list on phones. Detail has Overview, Details, Users and Forms tabs. Users shows direct assignments plus people inherited from above (one row per person, sources listed); roles and JSON overrides are edited in a side sheet with a live effective-permission preview. View as starts from a user row or the top bar and opens on the Forms list. |
| P20 | Frontend rules source | D27 | Cobley's frontend code is discarded; its backend and its behaviour rules are kept. Rules live in three places kept in sync: the Fomu frontend rules doc, FRONTEND_RULES.md in the repo (read by CLAUDE.md), and the Rules tab on the prototype's Design system page. |
| P21 | Permission action names | D28 | Module.action with Cobley's verbs: list (was view), view (one record), create, edit, delete, plus module-specific actions (Forms.publish, Responses.export, Users.impersonate). Menus are gated by Module.list. |
| P22 | Contextual search | D29 | The top-bar search box follows the page. | P23 | Global search and Dashboard | D30 | A Dashboard is the new home page. | P25 | Refresh everywhere | D32 | Every viewable page (lists, details, results, dashboard) has a Refresh button with an 'Updated x ago' hint. Refreshing keeps the current content on screen, dimmed, until new data arrives; only a first load with nothing on screen shows a spinner. |

| P27 | Approvals screens | D34 | Approvals menu: Inbox (Waiting for me / My requests / All or My locations) and Delegations; Configuration › Approval workflows. | P28 | Component library | D35 | COMPONENTS.md is generated from the prototype's component inventory (specs) and components_api.json (props, emits, slots, do/don't). | P29 | API select paging and labels | D36 | Mixed paging per module: page= for small tables, opaque after= cursor for big or busy ones; has_more instead of totals; next page loads when an end marker scrolls into view. | P30 | View as: person or role | D37 | View as has two read-only modes: a real person, or a role preview built from a main role plus an optional custom role at a location (no real person; a synthetic member that is never listed). | P32 | Roles as list + details | D39 | Roles follow the core-module shape. /roles is a list (KPIs, All/Main/Custom tabs, toolbar with refresh, filters for type, people and permission count, sort; rows show permission coverage, visible menus and holders). /roles/{id} is a details page: Overview (KPIs, permissions by module, about + timeline, holders), Permissions, Menus, People, History; tab in ?tab=. | P33 | Short approver steps | D40 | A step needing 2+ approvals must have at least required + 1 people who can approve anywhere in the org, because the requester never approves their own request; single-approval steps need 1 (escalation to owners and admins covers the rest). The workflow editor shows the count, blocks Save and blocks switching it on. Existing workflows that fail are flagged “Can’t be met”; at runtime a short step adds the Owner, needs only as many approvals as people can give, and an Owner can complete a step that already has every approval it can get (logged as is_owner_override). |
| P34 | Staged role edits | D42 | Permission and menu ticks on a role are staged. A sticky bar shows +added / −removed and how many people it affects, with Discard and Save. | P35 | Approval notifications | D43 | Channels: in-app (always), email, SMS via NJIWA, push (NativePHP). A step may override channels and mark them required. People opt out of email/SMS/push in Notification settings; required steps ignore that. Every send is a notification_deliveries row (sent or skipped with reason) shown on the request’s Notifications tab; requesters and admins can send a reminder now. | P36 | Approval email and quiet hours | D44 | Approval emails carry a link to the request only; approvers sign in (with 2FA) to decide. No signed one-click links. Stored in organizations.settings.quiet_hours {on, from, to}. |
