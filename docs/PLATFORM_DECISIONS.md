# Platform decisions (P-log)

> These are decided for every product on the platform. A product inherits them and never re-opens them; it keeps its own D-log for product decisions. Change a P only here, with a new P that supersedes it, then update the kit prototype, rules and components in the same commit. Each entry notes the Fomu decision it came from.

| P | Decision | Was | Detail |
| --- | --- | --- | --- |
| P1 | ID strategy | D4 | ULID for every record that appears in a URL or is shared outside the app; bigint for internal tables. |
| P2 | Admin sign-in | D7 | Email, phone or username + password, then TOTP 2FA (Fortify). Optional 30-day trusted device; org can require 2FA. |
| P3 | Roles and menu access | D8 | Cobley-style JSON roles (spatie removed). roles.permissions is a JSON array of permission names in Module.action form (Forms.list, Forms.create, Responses.export; see D28). One permission per child menu; parent visible if any child is (OR); empty parents hidden. Missing permissions go to a role first, to a single user (granted_permissions on user_locations) only as an exception. |
| P4 | Menus, selects and popovers never clip | D9 | Always use shadcn-vue *Content components (DropdownMenuContent, SelectContent, PopoverContent, TooltipContent) with their portal on and collisionPadding 8. Never position a menu with absolute inside a scrolling or overflow-hidden container (tables, card lists, dialog bodies). |
| P5 | Clickable cards with actions | D10 | A card that opens on click uses a stretched link; its action buttons (menus, toggles) sit above it with relative z-10 so they stay tappable. |
| P6 | Tables on phones | D11 | Below 640px every data table switches to a compact card list (forms list, responses, members). The table/cards toggle only applies from 640px up. |
| P7 | Server-side access matches the menu | D12 | Every route and API endpoint behind a menu checks the same permission (Laravel middleware can:<permission>). Hidden menu = 403 on direct visit, shown as a 'No access' page with a request button. |
| P8 | Page transitions | D13 | Curtain plays on first app load (starts closed with 'Loading…', opens once the app is ready; the closed curtain is in the server HTML so nothing flashes) and on every page change, sidebar navigation included (revised 10 Oct). Not between sign-in steps or between tabs inside a page. Loader appears only if the next page takes longer than 300ms. Skipped with prefers-reduced-motion and switchable off in the prototype. Curtain colour has its own tokens: bright teal (--curtain 170 62% 46%, dark text) in light mode, deep green (166 58% 13%, light text) in dark mode. |
| P9 | Sidebar menu animation | D14 | Animation follows the display mode by default (dropdown: expand + stagger, panel: slide, rail flyout: fade); per-menu override in Menu Management. Dropdowns are always accordion. Forms and Configuration cannot be hidden. |
| P10 | Menu Management layout | D16 | The page is information only: parent/child rows (drag to reorder, drag a child onto another parent to move it) showing type, permission, who sees it and status. All editing happens in a gear popup: name, icon, parent, position, group heading, display mode, animation, permission and visibility. Parents stay top level. |
| P11 | Design system reference | D17 | The prototype's Design system page is the source of truth for tokens (colour, type, spacing, radius, shadow, motion, z-index, breakpoints), the component inventory with sizes and variants, and layout rules. The build copies its values into tailwind.config and the shadcn-vue theme CSS; any change is made there first. |
| P12 | Shared platform core | D18 | Identity, organisations, roles, permissions, menus, statuses, locations, wards and approvals reuse the Cobley Platform core. Every tenant-owned core table gets organization_id; system rows (roles, location types, statuses) keep it NULL and are shared. |
| P13 | Main role vs location roles | D19 | One MAIN role per organisation member (organization_users.role_id, role_type = system: owner, admin, editor, viewer). Several CUSTOM roles per location in user_locations.roles (JSON array of role ids, role_type = custom). A main role can never be stored as a location role; validated on save. |
| P14 | Overrides stay JSON | D20 | granted_permissions / denied_permissions / roles stay JSON on user_locations. Mitigations: MySQL 8 multi-valued indexes (CAST(... AS CHAR(80) ARRAY)) for 'who has X' queries, a FormRequest rule that every value exists in permissions.name, every change written to the activity log with before/after, and a migration that renames values when a permission is renamed. |
| P15 | Effective permission rule | D21 | At a location: main role permissions UNION custom-role permissions at that location and every ancestor (via location_closures) UNION granted_permissions, MINUS denied_permissions. Deny always wins. Result cached per user + location, busted when any input changes. |
| P16 | Statuses | D22 | Master-data status (users, organisations, locations, roles, request types) uses the statuses table (status_id). Workflow states that drive code (forms, attempts, responses, requests) stay ENUM columns. |
| P17 | View as | D24 | Admins with Users.impersonate can preview the app as another user or as a role (D37): read-only, a banner shows who is being viewed, no writes, no OTP or emails. Each session is recorded in impersonation_sessions (who, whom, location, started, ended). |
| P18 | Approvals are core | D25 | The Cobley approval engine (request_types, steps with role/permission/user approvers and or/and combinators, requests, request_approvals, delegations) is part of the core. First request types: Publish form, Export responses, Reset respondent. Approvers are resolved at the request's location and its ancestors. |
| P19 | Locations screens | D26 | List is a tree table (expand/collapse, search keeps matching rows with their ancestors) that becomes an indented card list on phones. Detail has Overview, Details, Users and Forms tabs. Users shows direct assignments plus people inherited from above (one row per person, sources listed); roles and JSON overrides are edited in a side sheet with a live effective-permission preview. View as starts from a user row or the top bar and opens on the Forms list. |
| P20 | Frontend rules source | D27 | Cobley's frontend code is discarded; its backend and its behaviour rules are kept. Where Cobley and the prototype disagree on look (list shape, fonts, theme), the prototype wins. Rules live in three places kept in sync: the Fomu frontend rules doc, FRONTEND_RULES.md in the repo (read by CLAUDE.md), and the Rules tab on the prototype's Design system page. |
| P21 | Permission action names | D28 | Module.action with Cobley's verbs: list (was view), view (one record), create, edit, delete, plus module-specific actions (Forms.publish, Responses.export, Users.impersonate). Menus are gated by Module.list. |
| P22 | Contextual search | D29 | The top-bar search box follows the page. Inside a module it searches that module only and filters the list in place through the module's own search filter (kept in the URL); a last line offers 'Search everywhere for ...'. On a details page it searches the parent module and shows a small dropdown. On pages with nothing to search the box is hidden. Every module declares a search filter field. |
| P23 | Global search and Dashboard | D30 | A Dashboard is the new home page. Its search is global: GET /search?q= runs each searchable module's existing select search and returns the top 5 per module, permission- and location-scoped, grouped with 'See all in X' links that open the filtered list. On phones a search icon expands into a full-width bar; on the Dashboard results open full screen with recent searches. |
| P24 | List toolbar | D31 | Order: Refresh, Filters (n), Clear, Sort, then the cards/table toggle and the primary New button on the right; Export/Import only when the backend has them. Filters dialog has Simple (natural operator per field) and Advanced (operator per field) modes; one request on Apply; filters, sort and page live in the URL. Status tabs stay as quick filters and stay in sync with the dialog. On phones the toolbar shows icons with counts and the dialog opens as a bottom sheet. |
| P25 | Refresh everywhere | D32 | Every viewable page (lists, details, results, dashboard) has a Refresh button with an 'Updated x ago' hint. Refreshing keeps the current content on screen, dimmed, until new data arrives; only a first load with nothing on screen shows a spinner. |
| P26 | Shared form behaviour from Cobley | D33 | Server-side drafts on every create/edit form (autosave 4s; create keeps several drafts with a picker; edit keeps one with a restore banner; never files or secrets; never in action wizards). No native pickers (select, file, date, time). Deletes need 'type YES'. Required fields use a CSS asterisk. Modals open through one modal host. Details tabs live in ?tab=. Related records open as a preview of the target's own details panel. |
| P27 | Approvals screens | D34 | Approvals menu: Inbox (Waiting for me / My requests / All or My locations) and Delegations; Configuration › Approval workflows. Request page shows the step timeline with resolved approvers and why, approve/reject (reason required), delegation labels and terminal banners. Actions behind an active workflow offer 'Request to …'. Nobody qualifying at the location chain escalates to owners and admins. |
| P28 | Component library | D35 | COMPONENTS.md is generated from the prototype's component inventory (specs) and components_api.json (props, emits, slots, do/don't). Screens are built only from it; a missing control is added to the library first. Contracts used by another module are extended, never changed. |
| P29 | API select paging and labels | D36 | Mixed paging per module: page= for small tables, opaque after= cursor for big or busy ones; has_more instead of totals; next page loads when an end marker scrolls into view. Selected labels: view endpoints return foreign keys as { id, label, sub } (selected-options), then one batched ids[] lookup per module per tick, then a shared label store. Current choices pinned on page 1. Archived, restricted and deleted values stay, flagged, with a warning; never cleared silently. 60-second cache with background refresh. |
| P30 | View as: person or role | D37 | View as has two read-only modes: a real person, or a role preview built from a main role plus an optional custom role at a location (no real person; a synthetic member that is never listed). Roles page offers 'Preview this role'. Full 'Act as' impersonation with write access is not part of Fomu. impersonation_sessions records role previews with viewed_user_id NULL and the role + location viewed. |
| P31 | Filter controls by data size | D38 | List filterFields declare select (short fixed sets, 10 or fewer, shown as pills) or select_paginated (anything that grows: locations, people, forms, wards), which renders a multi API select for its module. Location filters include descendants by default via location_closures, with a switch; the chip reads 'and below'. The list endpoint receives filters[loc][operator]=in&filters[loc][value][]=…&filters[loc][below]=1. |
| P32 | Roles as list + details | D39 | Roles follow the core-module shape. /roles is a list (KPIs, All/Main/Custom tabs, toolbar with refresh, filters for type, people and permission count, sort; rows show permission coverage, visible menus and holders). /roles/{id} is a details page: Overview (KPIs, permissions by module, about + timeline, holders), Permissions, Menus, People, History; tab in ?tab=. Header promotes Preview this role next to Edit (the role's defining action, like Add child on a location); Copy permissions from, Duplicate and Delete sit in More. Main role names are fixed; only custom roles can be created, renamed or deleted, and delete is blocked while anyone holds the role at a location (role_user_location rows). Permission ticks save immediately and apply on the next request. GET /roles returns perms_count, holders_count, menus_visible; GET /roles/{id}/holders returns main-role users or custom-role holders with their locations. |
| P33 | Short approver steps | D40 | A step needing 2+ approvals must have at least required + 1 people who can approve anywhere in the org, because the requester never approves their own request; single-approval steps need 1 (escalation to owners and admins covers the rest). The workflow editor shows the count, blocks Save and blocks switching it on. Existing workflows that fail are flagged “Can’t be met”; at runtime a short step adds the Owner, needs only as many approvals as people can give, and an Owner can complete a step that already has every approval it can get (logged as is_owner_override). |
| P34 | Staged role edits | D42 | Permission and menu ticks on a role are staged. A sticky bar shows +added / −removed and how many people it affects, with Discard and Save. Copy permissions from stages too. Leaving with unsaved changes (any nav, breadcrumb, sidebar, search, or closing the tab) asks Stay / Discard and leave / Save and leave. Save is one PUT /roles/{id}/permissions with the full set and is audited as one change. |
| P35 | Approval notifications | D43 | Channels: in-app (always), email, SMS via NJIWA, push (NativePHP). Workflow sets default channels and events: step waiting (approvers), reminder every N hours up to M times (approvers who have not acted), escalation or short step (Owner), decision (requester). A step may override channels and mark them required. People opt out of email/SMS/push in Notification settings; required steps ignore that. Every send is a notification_deliveries row (sent or skipped with reason) shown on the request’s Notifications tab; requesters and admins can send a reminder now. Email carries a link to the request, never one-click approve. |
| P36 | Approval email and quiet hours | D44 | Approval emails carry a link to the request only; approvers sign in (with 2FA) to decide. No signed one-click links. Organisations set quiet hours (default 20:00–07:00 EAT, on): SMS and push raised inside the window are held (notification_deliveries.status = held) and sent when it ends; in-app and email go at once; steps marked notify_required ignore quiet hours. Stored in organizations.settings.quiet_hours {on, from, to}. |
| P37 | Repository and stack | D45 | Each product is a monorepo: api/ = Laravel (laravel/framework ^13, from the Cobley backend, trimmed of modules the product does not use), web/ = Vue 3 + Vite + TypeScript + Tailwind + shadcn-vue SPA. docs/ holds the runnable prototype (visual source of truth), screenshots, decisions, ERD, frontend rules and component specs. Work is delivered in phases, one PR each, with screenshots compared against the prototype. |
| P39 | Scoped lists, one-card lists, linkable views | DevBiz D72, D73 | **Scoped lists:** a details tab (or page-level tab) that shows records is the module's own list with `useList({ scope: () => ({ fieldKey: parentId }) })`: rows locked to the parent (never a removable chip), the parent's filter field, column and search removed, quick tabs counted within the scope, its own search box (the top bar keeps searching the parent module, P22), no Refresh or context line (the page header has them), rows open the record's preview (P26), Export = CSV of exactly the rows shown with the parent in the file name, create opens the normal form with the parent shown locked (LockedField). **One card:** every list that shows rows, on list pages and in tabs, is one ListCard: search + quick tabs (one row only when they fit, by content not breakpoints; wrapped tabs sit left) / Filters, Clear, Sort (Refresh on list pages) on the left and Export, Copy link, create on the right / chips / optional summary strip / rows; the card switches table (≥ 700px card width) and row cards by its own width (container query), tables fill the card with no sideways scroll. Card grids (forms, media, delegations) keep ListToolbar. **Links:** route, record, `?tab=` and the active list's search, sort and filters are in the address (pushState on navigation and tab change, replaceState on filter changes); Back/forward, reload and pasted links restore the view; links never bypass permissions; dialogs and drafts are not in links. Extends P6, P24, P26. Tested in DevBiz before the kit change. (P38 is reserved for the curtain-colour proposal, DevBiz D23.) |
| P40 | Priority columns, one row shape, one list stack | kit exploration 2026-10-15 (COBLEY row list + Fomu ListCard) | **Priority columns:** every list that shows rows is one ListCard whose rows are a grid driven by the module's columns. One `identity` column (name/number + icon tile; never folds; keeps 40% of the card) and at most one `hero` number (never folds; right-aligned, tabular). Every other column has a `priority` and a `fold` target; as the card narrows (its own width, one ResizeObserver) the highest-priority-number column folds first until the rest fits. Status folds right as a badge level with the title with the hero under it, shown on every row once folded. Identity badges (SKU, record no.) fold onto the title line. Meta columns fill the row's meta line in priority order while they fit on two lines; the remainder is a `+N more` chip that opens a label/value strip under the row (page state, not link state). Header shows unfolded columns only; header click sorts; the Sort control reaches every column. Nothing in a ListCard scrolls sideways; report tables (Logs, Queue) are not ListCards. **Removed:** the cards/table toggle and per-user view memory (P24), phones-always-cards (P6), the 700px table/cards switch and the search+tabs share-a-row rule (P39). One mode only; a `density: full` label/value row was explored and dropped. **Stack**, every list, every width: toolbar · quick tabs (own scrollable pill row, only when declared) · search (own row) · chips + summary · column header · rows · footer. Tabs above search (coarse to fine). **Per module:** columns, priorities, hero, base meta, tabs, search placeholder. Identity leads with what a person recognises, never a bare id. Reference: `docs/platform/p40-priority-columns.html`, `docs/platform/P40-priority-columns.md`. |
